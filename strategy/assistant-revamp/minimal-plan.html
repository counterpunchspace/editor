Flash reliability and caching

The smallest set of changes that makes today’s DeepSeek Flash assistant fail less, fall back correctly, answer faster, cache its prompts and run strictly ZDR. No model picker, no UI, no new statistics tables. The big revamp plan stays as it is; everything here is a subset of its P0 and P0b, adjusted to what the code actually does.

Every step works from the first request, with no measurement period. Pushing and releasing are not part of this plan; they happen separately when the work is done.

What the code does today

Mapped by three readers and checked by a reviewer per step, with file and line references in every step below.

  • Provider picker. An hourly cron calls /api/ai/route. chooseRoute resolves the newest dated Flash model, filters endpoints by tools, context, quantization and uptime, ranks them by a price that already weights the cache-read price at 65%, and probes the top 8 with a multi-round tool conversation. A probe also fails if fewer than half of its later prompt tokens were cached. The best 4 by price and speed are stored in D1 ai_routes.
  • Requests. Each round sends order = only = the stored 4, plus data_collection: "deny". No zdr flag exists anywhere in the website code. Luna, the fallback, sends only data_collection: "deny" and isn’t pinned to any provider.
  • Fallback and demotion. A failing Flash step is redone on Luna. Any pre-stream Flash failure, even a 413 for an oversized chat, demotes an empty provider name (which removes nothing), marks the route stale and starts a full re-probe.
  • Prompt prefix. The editor puts the edit permission and the full, pretty-printed editor state into the system prompt and rebuilds it every round. Any text, caret, location or feature change breaks the cached prefix for the whole history behind it. The glyph filter chat does the same with the current filter code.
The biggest reliability problem.

chooseRoute never throws: when the OpenRouter catalog call fails or every probe fails, it returns an empty provider list. refreshRoute stores it with a fresh timestamp, and every request then goes straight to Luna until a later refresh succeeds, up to about an hour. One catalog hiccup at the top of the hour switches Flash off for everyone.

A1

A failed refresh keeps the last good route

Reliabilitywebsite
Why

The problem in the box above: an empty refresh result overwrites a working route.

Change

In refreshRoute (utils/ai-route-store.js:98-115): read the stored route first. When the new result has no providers and the stored one has some, keep model and providers_json, write the new warnings plus “refresh found no endpoint; kept previous route”, set refresh_started_at = NULL so the lock doesn’t block retries, and back-date checked_at to now − 80 min so the Assistant’s 90-minute stale check retries on the next traffic about 10 minutes later. The hourly cron retries anyway. Return the kept route. Store an empty route only when there was none, or the stored list was already empty. A route is kept only if it was chosen under the same rules: the A7 migration adds a policy column ("zdr-v1"), storeRoute writes it, and a stored route with another or no policy is never kept, so a route picked before ZDR can’t survive the change.

Policy mismatch means stale. readRoute callers treat a stored route whose policy isn’t the current one exactly like a route that is too old: the deploy health check’s ensureRoute and the first Assistant request both start a refresh straight away, in the background, instead of waiting 55 or 90 minutes. Until it finishes (one probe run, about a minute or two), requests still use the old route and answer, at worst through Luna. Raising the policy version later (zdr-v2) forces a fresh route on the next deploy the same way.

This also applies when every probe failed. That can be a real outage, but it looks the same as a key or probe-side problem, so keeping the old route is the safer default. If the endpoints really are gone, each request makes one failed Flash call before Luna: extra latency, no errors.

Test

test/ai-route-store.test.js: with a stored 2-provider route, a failing /models call and an all-probes-fail run both keep providers_json, write the warning, set checked_at to the back-dated value and clear the lock. No stored route, or a stored empty list, still stores the empty result. A stored route with no policy makes ensureRoute refresh even when checked_at is recent, and the Assistant request path schedules a background refresh for it.

A2

Re-probe only on failures a re-probe can fix

Reliabilitywebsite
Why

Every pre-stream Flash failure calls reportFlashFailure(env, waitUntil, "", …) (assistant.js:458). A user’s oversized chat (413), an exhausted credit (402) or a rate limit (429) therefore marks the route stale and probes 8 endpoints, for everyone. The refresh lock limits this to about one probe run every few minutes, but each run can reorder providers and cost cache hits.

Change

Decide on the raw upstream.status, not the mapped failure.status, because upstreamError maps OpenRouter 401/403 to 502 (:275-276) and a bad key would otherwise trigger probes that fail the same way. Call reportFlashFailure for a thrown fetch, for 5xx that isn’t a mapped 401/403, and for 404, which is how OpenRouter reports that no endpoint in only is available. Only log 400, 402, 408, 413 and 429.

In demoteProvider, return early for an empty key so an anonymous failure doesn’t zero checked_at. That part is tidy-up only: the re-probe itself comes from the refreshRoute call in reportFlashFailure, which the status gate controls.

Test

Flash 413: Luna answers and the D1 row is untouched. Flash 401: no refresh. Flash 503 and 404: a refresh is scheduled (await the captured waitUntil promises). demoteProvider(DB, "") leaves the row unchanged.

A4

Always finish a step, even without a usage chunk

Reliabilitywebsite
Why

finishStep sends done, bills and runs the empty-reply guard, but only runs when a chunk carries usage (assistant.js:773-808). If a stream ends without one, nothing after the loop (:813-814) sends done: the client keeps a possibly empty reply as final, billing is skipped, and an empty Flash reply never falls back to Luna.

Change

Track lastUsage on every parsed chunk, and after the loop add if (!doneSent) await finishStep(lastUsage). An empty guarded Flash step then throws into the existing Luna redo. Billing can’t double-count: addGenerationCostToBillingRun skips generation ids it already recorded. Don’t send done on the Luna error path at :830-836; it already sends an error and closes, and a done there would look like a successful empty reply to every editor build.

Test

Flash text with finish_reason but no usage: one done, billed once. Flash with no text, no tools and no usage: a Luna redo with fallback: true. A Luna stream with an error chunk: the error comes before any done and the stream closes. The existing tool-call case still sends exactly one done.

A5

Keep the first provider unless it fails or is clearly worse

Cachingwebsite
Why

Every round sends the stored order, and the hourly ranking adds half the probe’s run time to the score. Run-to-run timing noise can swap first and second place with nothing really changed, and every running chat then lands on a cold cache.

Change

Add an exported helper keepPrevious(ranked, previousTag, margin = 0.15) in plugins-worker/review/ai-route.mjs: if last hour’s first provider passed this probe run and scores within 15% of the new best, it stays first; the rest follow by score. chooseRoute gets an optional previous argument, applied after rankProbes (:554-556); without it, ranking is exactly as today. refreshRoute reads the stored route and passes its first provider.

This is global and best effort. A real price change across a time-of-day pricing window can still take first place (intended), and a demoted provider makes the old second place the new first.

Test

test/review-route.test.js: the previous first at 1.1× the best score stays first, at 1.3× it loses, a failed or missing one changes nothing, and no previous gives today’s order. test/ai-route-store.test.js: a seeded route keeps its first provider through a refresh where the second is slightly faster; after a demotion, the old second is promoted.

Note

ai-route.mjs also drives the PR-review plugin worker (route.mjs, server.mjs), which is why the new argument must be optional.

Privacywebsite

Not a reliability fix, but the one thing the assistant promises that it doesn’t enforce: data_collection: "deny" excludes training, not retention for abuse checks. It goes in this release because the routing code is open anyway.

Remove the duplicate constant at assistant.js:54.

If Luna has none, choose a different fallback before shipping, never a fallback that always fails.

A7

Faster first answers: shared prefix, real speed, speed under a price ceiling

Speedwebsite
Why

Before a chat’s own cache builds up, speed depends on which provider answers. Today speed is one timing per provider from the hourly probe conversation: it mixes queueing, thinking and output into one number, is noisy (the reason A5 exists), and is added to price with half the weight, so a slightly cheaper endpoint beats a much faster one. A Flash prompt costs about a cent; a few seconds of waiting matter more.

Change

a) Shared prefix for first prompts. After B1, the system prompt and tools are byte-identical for every user, several thousand tokens before the user’s own words, and all requests use one OpenRouter account. With A5 sending new chats to the same first provider, that prefix should stay cached there, so even a chat’s first prompt starts partly cached. No code beyond B1 and A5; A0’s first_prompt and cached_tokens show whether providers share the cache across requests from one account.

b) Real speed per provider. A small D1 table, ai_route_speed (tag, ttft_ms, tokens_per_s, created_at), no user id and no content. finishStep inserts one row per Flash step in waitUntil; the endpoint tag is exact, because A8 sends every Flash request to one tag only. The route refresh takes, per tag, the median of the newest 200 rows from the last 24 hours, and deletes older rows. With fewer than 20 rows it falls back to OpenRouter’s published endpoint latency and throughput if the endpoints payload carries them, otherwise to the probe timing.

c) Rank by speed under a price ceiling. A new assistant-profile ranking after the probes: every endpoint that passed and costs at most 1.3× the cheapest passing workloadPrice is a candidate; candidates are ordered by expected reply time, ttft_ms + 600 tokens ÷ tokens_per_s; endpoints above the ceiling follow by price. A5’s keepPrevious margin then applies to this reply time instead of the old score. The review profile keeps rankProbes unchanged.

Quality stays gated. Speed only orders endpoints that already passed everything: the probe and its caching check, the fp8-or-better quantization rule, the exclusion of turbo, fast, flex and spot endpoints, the uptime limits, and the reply guard’s demotion on a broken reply.

Test

test/review-route.test.js: within the ceiling the faster endpoint wins even when 20% dearer; above the ceiling price decides; with too few samples the fallback timing is used; the review profile’s order is unchanged. test/ai-assistant-fallback.test.js: a Flash step writes one speed row with the right tag and no user data; a Luna step writes none. test/ai-route-store.test.js: the refresh uses the median and prunes rows older than 24 hours.

Note

Needs a migration adding ai_route_speed to schema.sql. Fully working from the first request: until a provider has 20 real rows, its speed comes from OpenRouter’s published endpoint figures if present, otherwise the probe timing, and the first route refresh after deployment ranks with that straight away. Real figures take over by themselves within hours of normal traffic.

A8

Pin each chat to its provider

Cachingwebsite
Why

A provider only has a chat cached if that chat’s previous request went to it. Today every request sends the whole provider list, and OpenRouter’s own stickiness is off because we set provider.order (its docs say so). So a chat can move whenever the list changes, and each move rereads the whole conversation at full input price: on DeepSeek through OpenRouter, cache reads cost 0.1× and writes 1×.

Change

One provider per request. The Flash target no longer sends the route list. It sends exactly one endpoint tag: {order: [tag], only: [tag], allow_fallbacks: false, quantizations, ...PRIVACY}, built by a new pinnedRouting(tag) next to routing(), which stays for the PR-review worker.

Which tag. The request body accepts an optional providerPin. If it is a tag in the current route (same policy), the request goes there (pin: "kept"). If it is missing, as on a chat’s first request or from an older editor build, the request goes to the route’s first tag ("new"). If it is no longer in the route, it goes to the first tag too ("moved"). Anything that isn’t a tag in the current route is ignored, so the client can never steer a request outside the ZDR route.

When the pinned provider fails before streaming (thrown fetch, 5xx, 404), the server tries the next tag in route order, one tag per request, and only after all of them falls back to Luna. A mid-stream failure keeps today’s Luna redo. Because each request names one tag, a failure demotes exactly that tag: demoteProvider gets the tag instead of a display name, which fixes the unreliable name matching found in the code map.

Telling the editor. The done event carries providerPin: the tag that served the step when Flash served it. When Luna served, it is left out and the editor keeps what it has; the server checks it again on the next request.

Test

test/ai-assistant-fallback.test.js: a request with a valid pin sends only with that single tag and allow_fallbacks: false, and done returns the same pin; no pin goes to the first tag; a pin not in the route, or not a tag at all, goes to the first tag; a 503 on the pinned tag retries on the next tag and done returns the new pin; all tags failing ends on Luna with no pin in done; a guard failure demotes exactly the served tag. test/review-route.test.js: routing() is unchanged.

Note

No new storage: the pin travels with the chat. Older editor builds send none, so all their requests land on the route’s first tag, which A5 keeps stable. That is already a pin in practice. No idle rule is needed: staying with the same provider is never worse, because if its cache has expired, any other provider would miss too.

B1

Static system prompt, editor state at the end

Cachingeditor
Why

buildSystemPrompt (assistant/profile.ts:51-61) appends the permission, the stale-script notice and the editor state to the system prompt, and streamRound rebuilds it every round (assistant/chat-session.ts:704-718). After any state change within a prompt, and nearly always between prompts, the whole history behind it is billed uncached. This is the largest caching win.

B3

Retry server failures and keep finished tool rounds

Reliabilityeditor
Why

Only dropped connections are retried. A 502/503/504, an in-stream error and a stream that ends without done all end the turn, and a stream without done is even kept as the final answer. When a turn fails, commit() never runs (chat-session.ts:551-558), so tool rounds that already edited the font vanish from history and the model no longer knows about its own edits.

Change

In streamRound: treat 502, 503 and 504 as a dropped connection, using the existing 3-attempt backoff. Not 429: that’s the user’s own hourly or daily limit (assistant.js:322-336), which a few seconds of backoff won’t clear. Treat a stream without done as dropped only when no tool calls arrived; with tool calls, run them as today. Treat an in-stream error event the same way, keeping the streamed text and generation id.

In send(), call commit() at the start of the error branch, and in the stop branch also when no text was streamed. At that point the history holds only completed rounds, so nothing needs trimming.

Test

Mock fetch with host.streamRound unset: 503 then 200 retries once; 429 doesn’t retry; a stream without done and without tool calls is retried; one with tool calls runs them once; a failure in round 3 leaves two complete rounds in the history, on error and on stop.

B4

Remember the provider with the chat

Cachingeditor
Why

The other half of A8: the editor is where the pin lives, so the server needs no storage.

Change

AssistantChatSession keeps a providerPin next to its conversation, never inside conversationMessages. streamRound sends it with every request, including each tool round within a prompt, and updates it from every done event that carries one. reset() (the + button) clears it; fork() copies it. The glyph filter chat uses the same class and gets it for free. When chat history is saved (big plan, P3), the pin is saved with the chat, so a reopened chat goes back to its provider.

Test

tests/assistant-chat-session.test.js with a mocked fetch: the first request has no pin; after a done with providerPin, the next round and the next prompt send it; a done without one keeps the old pin; reset() clears it; fork() copies it; the pin never appears in conversationMessages.

Left out on purpose

  • OpenRouter cache options (prompt_cache_key, cache_control). DeepSeek caches the prefix automatically; B1 and B2 fix the prefix.
  • Cache-write price and measured cache mix in the ranking. The ranking already weights cache reads at 65%, and changing the formula now would fight A5.
  • Feeding real cached_tokens back into ranking. Needs per-endpoint stats storage. A0 first shows whether endpoints differ.
  • Moving refreshes off waitUntil to a queue or alarm. A1–A3 remove most of the harm a cut-off background refresh can do.
  • Discarding a failed Flash step’s text before Luna’s redo. A real problem, but it needs a new stream event and visible UI change. It stays in the big plan.
  • History trimming, the forced summary round, duplicated round texts. None break caching; they belong to the big plan.
  • Staging route freshness. The cron targets production only; staging relies on the deploy health check and the stale trigger.

Open questions the checks answer

  • Whether providers share prefix caches across requests from one account (A7a). The smoke test shows it; everything works either way.
  • Whether OpenRouter’s endpoint list publishes latency and throughput (A7 fallback). Checked before deploying; without it, the probe timing is the fallback until real rows arrive.
  • Whether Auto Exacto reorders an explicit order plus only. Visible in the A0 provider field; if it does, add allow_fallbacks: false in a follow-up.
