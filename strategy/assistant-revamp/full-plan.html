Counterpunch editor · plan · 22 Nov 2026

Assistant revamp

Chat history per font, a model picker with live per-prompt prices, strict ZDR for every model, image input, and a set of new reference and vision tools. This plan is based on a read of the current code in editor/ and website/ and on live OpenRouter data from today.

What I found first

Today’s traffic is not strict ZDR.

Provider routing in website/plugins-worker/review/ai-route.mjs sends only data_collection: "deny", and that is not a ZDR guarantee. The Luna fallback in website/utils/ai-settings.js isn’t pinned to a provider either, so it can reach OpenAI directly. Every request needs provider.zdr: true, with closed models pinned to their ZDR hosts. This fix stands on its own and should ship first.

  • Chats exist only in memory (AssistantChatSession.transcript and conversationMessages). fork() already serializes them to JSON, which is a good start for a storage format.
  • Today the server picks the model. The client sends no model, and GET /api/ai/settings already returns a model list that nothing reads.
  • No images are sent anywhere, and the canvas has no image export. Preview mode, the filled text view, already exists in renderer.ts.
  • Per-prompt cost is recorded exactly, in D1 assistant_billing_runs. Nothing records which chat a prompt belongs to, or where it falls in that chat.

Routing

  • Open-weight models use the internal provider picker. Extend ai-route.mjs with one routing profile per model. It probes only endpoints on OpenRouter’s ZDR list (/api/v1/endpoints/zdr) that also pass the tool-calling probe plus a new image probe, then ranks them by price and speed as it does today. Each request carries zdr: true and the stored order/only lists.
  • Closed models get hard defaults, with no probing. GPT goes to only: ["azure"]. Claude goes to order: ["amazon-bedrock","google-vertex"] with allow_fallbacks: false. Both send zdr: true. Claude also needs cache_control breakpoints on the system prompt and tools, or long chats will cost several times more.
  • Caching comes first (details in “Caching rules” below). A chat stays on the provider that answered its first prompt.
  • Fallback. Requests with no model choice keep today’s Flash → Luna fallback, now Azure-only. A model the user picked explicitly never switches. Inside that model, the router can still try its next ranked ZDR provider. If every provider fails, the chat shows an error such as “Claude Opus is unavailable right now. Try again, or pick another model.” with a Retry button.
  • Auto Exacto. OpenRouter reorders providers by tool-call quality by default (docs), on every request, which breaks cache stickiness. We opt out. Our explicit order/only list with fallbacks off decides, and our own quality signal replaces theirs.

Caching rules

In an agent chat, nearly all input tokens are the resent history. A cache hit costs 5–10% of the normal input price, so a warm cache saves more than the price difference between any two providers. The routing decider therefore puts caching above price and speed.

  1. Sticky provider per chat. The first prompt of a chat picks the provider. Every later prompt and tool round in that chat sends that provider alone as only, with allow_fallbacks: false. That holds even after the hourly route refresh ranks a different provider first, and even when the quality score drops a little. The route refresh applies to new chats only.
  2. Switch only on failure. The chat moves to the next provider only if the pinned one errors, fails the reply guard, or drops out of the ZDR list. The new provider then becomes the pin. A chat idle for over 30 minutes may move to the current best provider, because caches expire by then anyway.
  3. Rank by cached cost. workloadPrice() currently weighs listed prompt and output prices. It changes to an agent-chat mix: about 80% of prompt tokens billed at the cache-read price. Endpoints without implicit caching get a large penalty, and cache-read prices vary up to 10× between ZDR hosts. The probe records whether the second step actually reported cached_tokens, and endpoints that claim caching but don’t deliver are ranked as having none.
  4. Keep the prompt prefix stable. Today buildSystemPrompt puts the live get_editor_state output and the edit permission into the system prompt on every round. That changes the start of the prompt, so nothing after it can be cached. The fixed parts (system prompt, then tool definitions) come first and stay byte-identical. Editor state and permission move into a short message at the end of each turn. Tool order is fixed and sorted.
  5. Closed models. Claude gets cache_control breakpoints on the tools, the system prompt and the newest message, using the 5-minute cache. GPT on Azure caches automatically; send prompt_cache_key = chat id where OpenRouter passes it through.
  6. Measure it. ai_prompt_metrics records cached and uncached input tokens per prompt. The internal view shows the cache-hit rate per model and provider, and a provider with a poor hit rate loses rank like one with poor quality.

Facts instead of descriptions

Hand-written descriptions like “strong at feature code” are either generic or misleading: what a model can do depends mostly on the tools we give it, and it changes with every version. So the cards carry none. Everything on a card is a fact or a measurement, and nothing needs editing when a version changes.

  • Speed has no line of its own; it only decides the Fastest badge. It is the median time from Send to a finished prompt over the same 200-chat window as prices, measured per version. ai_prompt_metrics gains duration_ms next to the time to first token it already records.
  • Badges. The cron gives out exactly three: Cheapest (lowest average prompt cost), Fastest (lowest median duration) and Best quality (highest quality score). Each goes to the single model leading that measure across the picker, comparing the “Latest” versions. Models with estimated prices can’t hold Cheapest. A tie is broken by the underlying unrounded value. A model leading two measures shows both. Badges move with the data, with a margin of 5% before a badge changes hands, so it doesn’t flicker between two close models.
  • What stays: the model name, the maker line for open-weight models (a fact that helps recognition), the version and its release date, ZDR, and the “default” and “new” tags. “New” shows for 14 days after a model family is added.
  • The handbook page Models and prices explains the badges along with the other numbers.

Model versions

Each model in the picker has a version menu. “Latest” is preselected and enough for most people. The menu also lists a short, automatically curated set of specific versions, for anyone who wants a version that worked well for them to stay put.

Fully automatic

  1. Catalog sync. The hourly cron job that already refreshes routes also reads OpenRouter’s model list (/api/v1/models). It matches new versions to our models by family, using one pattern per model in the registry, such as deepseek/deepseek-v*-flash*. Adding a model family is the only manual step: one config line.
  2. Gate. A new version is listed only if it takes image input, supports tool calling, has at least one strict ZDR endpoint, and has no expiry date within 30 days.
  3. Benchmark. A version that passes the gate gets a benchmark run straight away. That gives it its first quality score, and only then does it appear in the menu.
  4. We decide what “Latest” means. “Latest” is the newest version that passed our gate and benchmark. We send OpenRouter the exact version id, never their ~…-latest alias. So “Latest” only moves after our own checks, every stat belongs to exactly one version, and caching isn’t broken by a change happening on OpenRouter’s side mid-chat.
  5. Curation. The menu shows “Latest” plus the newest 3 versions that pass the gate. Older ones drop out of the menu, and their stats age out with the 180-day limit.
  6. Retirement. If a pinned version loses its ZDR endpoint, fails the gate, or is withdrawn, the next prompt uses “Latest” instead. The chat shows a one-line notice: “DeepSeek Flash v4 is no longer available, so this prompt used v4.1.” The saved choice switches to “Latest”. A restored chat whose version is gone continues the same way.

Stats per version

  • Prices and quality are stored per exact version. A specific version’s row shows its own figures.
  • A new version inherits prices as seed rows. When a version is promoted, the cron copies the previous version’s newest 10 chats (each chat’s first-prompt cost and costliest-prompt cost) into the new version’s window, flagged seed. The normal averaging then runs over seeds and real chats together: the first finished real prompt already moves the range, after 10 real chats they weigh half, and the seeds are the oldest rows, so the 200-chat window drops them first. There is no switch-over threshold. Quality starts from the version’s own benchmark score.
  • The model card shows the figures of whichever version is selected, so the card and the menu always agree.

Simple for the user

  • The card shows the maker (open weight only), at most an automatic badge, the two stat lines (Quality, Per prompt) and the selected version as small text (“Latest · v4.1 (17 Oct)”). The version menu appears only when it’s tapped.
  • Version rows use exactly the same two stat lines as the card, under the version name and release date. There are no provider names, ids or token prices.
  • A “How these numbers work” link in the picker footer opens the new handbook page Models and prices (see “Assistant documentation”), which explains the dots, the price ranges, versions and routing in plain words, and that everything is measured automatically and never includes your chats or fonts.
  • Each reply’s model label in the chat shows the exact version used, such as “DeepSeek Flash v4.1”. That is saved in the chat history too.

1 · Chat history per font

Storage key

Use the document key from documentKeyFromUrl (disk:///id/name, cloud:///assetId, github://…), normalized so that cloud:// and cloud:/// match. When a font gets a new identity (save-as, or a new font saved for the first time), noteDocumentIdentity() moves its chats to the new key. new:/// drafts stay in memory until they are saved. memory: example fonts aren’t persisted.

  • cp.assistant.chats.v1:<docKey> holds the index: id, title, createdAt, updatedAt, model, prompt count and cost.
  • cp.assistant.chat.v1:<chatId> holds one chat record.
  • Records are compressed with CompressionStream("deflate") and base64-encoded. Keep at most 50 chats per font, with LRU eviction across fonts when setItem hits the quota.

What a record stores, hidden details included

  • The full transcript: every entry kind, automatic, each item’s round and usage, and for each tool call its args, result, failed and previousContent. timeLabel is stored as the original string and never recomputed, so times look the same in another locale or time zone.
  • conversationMessages and sessionTotals, so you can carry on a restored chat.
  • New per-reply metadata that is also displayed: the model key, plus the served model and provider from the done event, which the client ignores today.
  • The Python document target identity and revision for each edit tool call. Reveal and Revert then work through the same revision check as today: when the file has changed since, they look the same as they do now for a stale edit.
  • Image references for snapshots, stored as content hashes. The images themselves go in IndexedDB (see decisions).
  • schemaVersion and rendererVersion.

Identical rendering: restoring calls the same AssistantChatView.render() on a rebuilt session. A Jest test runs a scripted chat, takes the panel’s DOM, saves and restores the chat, and requires the DOM to match exactly. Any change to the renderer must keep old records rendering the same way, which is why records carry rendererVersion.

Glyph filter chats

FilterChatRegistry keeps its per-path chats in sessionStorage under cp.filterchat.v1:<docKey>:<path>, so a reload no longer loses them, but closing the tab does. There is no history and no picker. Expert mode gets a “Clear chat” item that empties the chat for this filter. There’s no undo, so it asks for confirmation inside the panel.

2 · Price ranges per model

  1. The client creates a chatId (a UUID) for each chat, and sends it with promptIndex and model on every request. Filter chats send it too.
  2. A new D1 table, ai_prompt_metrics, gets one row per prompt with only these columns: chat_id (random, not linked to the user), prompt_index, model_key, provider, surface, cost, created_at, token counts (uncached input, cached input, output, reasoning, image), a seed flag, plus the counters from the quality section. It has no user id and no prompt text, reply text, tool arguments, tool results or font data. One prompt is one billing run: the user message plus every tool round it triggers. Cost is the amount charged to the user, including fee and VAT, so the range matches the bill. A Jest test checks the insert against a fixed column list, so text fields can’t be added later by accident.
  3. Window by count, not by days. The window is a fixed number of recent chats per model, so a rarely chosen model like Opus keeps as much data as Flash.
    • Prices: the newest 200 chats per model.
    • Quality: the newest 500 prompts per model and provider.
    • Age limit: 180 days, so very old data still goes even for a model nobody picks.
    • New version: quality starts from the new version’s benchmark score. Prices start from 10 seed rows copied from the previous version and are averaged with real chats from the first finished prompt on (see “Model versions”).
    • Price changes don’t throw data away. Stored costs are rescaled by the ratio of new to old listed price.
  4. The cron deletes rows outside the window (a ROW_NUMBER() query per model in D1) and older than 180 days. Then it recomputes ai_model_price_stats per model from all chats in the window, across every user:
    • Low = max(1, round(mean cost of prompt 0 across chats))
    • High = max(low, round(mean, across chats, of the costliest prompt in that chat))
    Only chats with at least two prompts count toward High.
  5. A price is always shown. There is no “collecting” state in the UI. A new version of a known model starts from seed rows copied from the version before it. A completely new model family has no predecessor, so it gets an estimate (below).
  6. The cron also stores avg, the mean cost of all prompts in the window, which the credit meter uses to turn a balance into “prompts left”.
  7. GET /api/ai/settings returns the models with their ranges, the estimate flag and the ZDR flag, and the picker reads it. Display rules: “1–3 ct”, “2 ct” when both ends match, “≈” only for estimates, and euros from €1 up (“80 ct–€1.40”). In overage, the client doubles every figure before formatting, matching what deductAiCredit actually charges (OVERAGE_MARKUP: 1.0).
  8. Price dots: five bands per prompt, up to 3 ct, 10 ct, 25 ct, 50 ct, and above. The dots from the low end’s band to the high end’s band are lit, coloured from green to red by band, so a narrow cheap range is one green dot and Opus lights three to five. The bands are fixed, so dots stay comparable across models and over time.

Estimating a new model family: token profile transfer

Listed token prices alone are a poor guide. Two models with the same price per token can cost very different amounts per prompt, because one thinks out loud for 4,000 reasoning tokens and the other answers in 300, and one caches well while another doesn’t. So the estimate multiplies the new model’s listed prices by a token count that reflects how this model behaves, scaled to real-world chats:

  1. The new model’s own token profile. The gate runs the benchmark before a model is listed anyway. The benchmark records, per task, the uncached input, cached input, output and reasoning tokens, and image tokens. Two task groups stand in for the two ends of the range: short single-step tasks for the first prompt, and the long multi-round tasks for the costliest prompt.
  2. The real-world factor. For every model that has real chats, we know both its benchmark token counts and its real-world token counts (from ai_prompt_metrics, which records token counts per prompt along with cost). Their ratio, per token type and per end of the range, says how much bigger real chats are than our tests. We take the median ratio across all models.
  3. The estimate. New model’s benchmark tokens × real-world factor × the listed prices of the provider the router would pick (cache-read price for cached tokens) × fee and VAT. That gives an estimated first-prompt cost and costliest-prompt cost.
  4. Seeded, then replaced naturally. The estimate is written as 10 seed rows, exactly like a version’s inherited prices. The first finished real prompt joins the average straight away, and real chats push the seeds out over time. One mechanism covers both cases.
  5. How it looks. While seed rows from an estimate outnumber real chats, the price dots are drawn as rings and the range carries “≈”, with the tooltip “Estimated from listed prices and how many tokens this model used in our tests. Real prices replace this as people use it.” After 10 real chats the dots fill in. A seeded new version of a known model is not marked, because its seeds are real chats.

Images raise cost. A 1024 px snapshot is about 1,200–1,350 input tokens on GPT and Claude, and it is resent with every later round of the chat. Snapshots count toward the stats like everything else. Default sizes come from the experiment below.

Quality indicator

Two levels, because users and the router need different things:

  • Per model and provider, internal only. This feeds the open-weight provider picker. Providers can serve the same weights very differently because of quantization, chat templates and tool-call parsers.
  • Per model, shown to users. The dots in the picker are the model as it actually runs for them, measured on whatever providers the router used. Users never see provider names, and there is nothing extra to choose.

The nightly benchmark

Today’s probe only checks that tool calls work, in a four-step file-reading conversation. I’d add about 12 font tasks with automatic grading, run against every candidate endpoint. Examples: add an anchor to these glyphs at every station; write a kern feature that compiles; write a glyph filter that matches these 14 glyphs; read the text in this snapshot back exactly. The snapshot task proves image input actually works on that provider and isn’t silently dropped. It costs a few cents per endpoint per night.

Scores and routing

  • Prompt success. A prompt succeeds when it had no server error, no tool-call error, didn’t end on a failed Python run, didn’t hit the round limit, and got no Stop, Retry, Revert, quick undo or thumbs down. A thumbs up cancels the soft signals on that prompt (Stop, Retry, undo within 2 minutes), which often mean “not quite yet” rather than “bad answer”. It never cancels a hard failure: a server error, a tool-call error, a failed tool run or the round limit. Thumbs down always makes the prompt a failure.
  • A score from the first prompt on. Every model and provider starts with a score from the benchmark before any user prompt exists. Live prompts then update it one at a time. The math is a Bayesian average: the benchmark result counts as 30 imagined prompts at its success rate, and each real prompt is added on top.
    • On launch day there are 0 real prompts, so the score is the benchmark score.
    • After 30 real prompts the two weigh the same.
    • After a few hundred, real use dominates and the benchmark only steadies it. A provider with 12 prompts isn’t ranked first or last by luck.
  • Seed before launch. The benchmark runs once for every model and provider before the picker ships: by hand from the dev script, then nightly from the cron job. A newly added model or provider gets a run when it is added, so it never appears without a score.
  • Live, not hourly. Each prompt’s outcome is added to running totals in ai_quality_stats (successes and attempts per model and provider) as the prompt finishes, so the dots move right away. The nightly job rebuilds the totals from the newest 500 prompts per model and provider, at most 180 days old, and swaps in the new benchmark result.
  • Routing for open-weight models: when a new chat starts, drop endpoints more than 5 points below the best, then rank the rest by cached cost and speed. The ranking only chooses a provider for new chats. Running chats stay on their pinned provider (see Caching rules). Today’s instant demotion on a guard failure stays, and it is also the one thing that moves a running chat.
  • User display: 1 to 5 dots per model, visible from day one. The model score combines its providers’ scores, weighted by how many prompts each provider served, or by the benchmark alone before any use. While a model has fewer than 30 real prompts, the tooltip says “Based on our tests so far.” After that it says “Based on our tests and how often prompts finish without errors and how people rate the replies in recent chats.” The dots look the same either way: no numbers, no providers.
  • Internal view: an admin page in the website, or to begin with a script over D1, listing each model and provider with success rate, error mix, benchmark score, speed and price.
  • Stumbles, internal only. The internal view also shows failed Python runs per prompt for each model, including the ones it recovered from. They never move the dots. If one model stumbles clearly more than the others on the same docs, that’s the model; if all models stumble alike, it’s our docs.
  • Docs first, enforced. The system prompt’s “Call python_api_docs before using unfamiliar model APIs” becomes “Before your first Python code in a chat, call python_api_docs.” The editor enforces it: execute_python_code, create_python_draft_in_editor, replace_python_document_in_editor and replace_python_text_in_editor are refused with “Read python_api_docs first” while no python_api_docs call exists earlier in the chat (by any model; a restored chat counts its earlier calls). The filter chat gets the same rule. A refused call doesn’t affect quality: the user never sees the wrong order, and the wasted round already shows in price and speed. Each refusal is counted per model in the internal view, next to the other stumbles. A test covers the block in both chats.
  • Docs report, later. An optional addition to the internal view: for failed Python runs, the exception class and the API member it failed on, checked against a list of our own API identifiers so no glyph names or font content get through. Ranked by frequency across models, it shows which doc pages to fix first. It never affects any score.

Thumbs up and down sit in the chat, under the last assistant reply of each prompt, and nowhere else. A tap records the rating and shows “Thanks for rating this reply.” Tapping the other thumb changes it, tapping the same one again removes it. There is no text box and no contact option: without the font and the chat, a written comment can’t be followed up, and we don’t want to store either. Ratings are also saved on the chat in localStorage, so the history shows them as they were. Filter chats get the same buttons in Expert mode.

Fits with ZDR and our own promise. A rating is a counter on ai_prompt_metrics: model, provider, prompt index, up or down. It has no user id and no content. In the quality score, a thumbs down makes the prompt a failure, the same weight as an error. A thumbs up cancels the soft signals on that prompt (Stop, Retry, undo within 2 minutes) but never a hard failure such as a server or tool error. A prompt counts exactly once either way, so ratings matter only as much as people use them.

Rules

  • Prompts left = remaining credit ÷ the selected model’s avg prompt cost, rounded down. Switching to a cheaper model visibly raises the number, which nudges people toward the right model without any lecture. The popover always names the default model’s count too.
  • When the meter appears: below 20% of the month’s included credit, or fewer than 20 prompts left on the selected model, whichever comes first. Amber, “≈ 12 prompts left”. The picker shows the same as a banner at the top.
  • Overage: only for active paid subscriptions with overage turned on, as today. The meter turns red and reads “Overage · ×2”. The chip, the picker and the version menu show every price doubled, in amber, and the picker banner says the prices already include the doubling. The popover shows the overage total so far this month (unreported_overage_cents).
  • The moment it starts: the prompt during which the credit runs out gets a one-line notice in the chat. Such a prompt is billed partly from credit and partly at double price, exactly as deductAiCredit splits it today.
  • Used up with overage off, or on the free plan: the input is disabled with the renewal date and the two ways forward. Free users see “Subscribe to Basic” instead of the overage option, as the server’s 402 message says today.
  • Higher plans: the low banner, the overage popover and the used-up state all say that a higher plan includes more credit at standard prices before overage starts, and link to plan comparison. Enterprise users, at the top of the plan order in plan-change.js, don’t see the line.
  • Data: the done event already returns balance and overageAllowed, so the meter updates after every prompt with no extra request. /api/ai/settings adds the month’s included credit, the renewal date and the overage total.

Image size experiment

This is planned, not started. The goal is to find the smallest snapshot size per model that still answers visual questions well.

  1. Test set: about 30 renders from fonts in gfsources/, each with a planted fault and a question with a known answer. Examples: a misspaced pair, a missing diacritic, a wrong contour direction showing as a hole, an uneven stem weight, a broken interpolation at a location, or reading back a line of text.
  2. Variables: longest side 256, 384, 512, 768 and 1024 px; PNG versus WebP; black on white versus grey; one full line versus crops of the line.
  3. Measured: the image tokens actually billed (the usage.prompt_tokens difference with and without the image), cost from usage.cost, and answer accuracy, graded automatically.
  4. Result: a default size per model at the knee of the accuracy curve, written into the model registry. snapshot_canvas then gets a region parameter, so the model starts with a small overview and asks for a sharper crop only where it needs one. That is cheaper than one large image, because every image is resent in each later round.
  5. Where it lives: a script next to ai-filter-cost.spec.ts, behind AI_IMAGE_E2E=1, so it never runs in CI by accident.

Several of these exist already: compile_binary_font, shape_binary_font, inspect_binary_font and execute_python_code. The new ones fill gaps in vision, reference, QA and context.

Vision

  • snapshot_canvas({maxSize?, location?}) re-renders the current text view in preview mode to an OffscreenCanvas on a solid background, with no handles or selection. It returns a PNG or WebP, plus the visible string and current location as text. Most providers don’t accept images in tool messages, so the image is attached as a follow-up user message part. The chat shows it as a thumbnail inside the tool card.
  • glyph_grid({glyphs|filter, location?}) renders a contact sheet with glyph-tile-renderer-fast.ts and returns an index-to-name map.
  • render_proof({text, sizes[], locations[], features}) renders a waterfall or interpolation strip from the compiled font.

Reference

  • fea_syntax({topic}) and spec_search({query, corpus}) / spec_section({id}). Bundle the AFDKO feature file spec (v1.27, October 2024, Apache-2.0, Markdown source in the afdko repo), split by heading, behind a small BM25 index. Each result includes its version and URL so answers can cite it.
  • opentype_table({tag}). On the spec question: Microsoft OpenType 1.9.1 (May 2024) is still the newest Microsoft release. ISO/IEC 14496-22:2026, the Open Font Format 5th edition, appears to have been published in July 2026, but I couldn’t confirm its contents or whether it is free. The name hasn’t changed; OFF has always been the ISO twin of OpenType. The licence for Microsoft’s text is unclear, so fetch pages live through a website proxy with a fixed list of table tags and a cache, instead of bundling them. Add avar2, beyond-64k and VARC from the boring-expansion repo once its licence is confirmed.
  • feature_tag_info, script_lang_tags, unicode_info and glyph_name_info use small bundled registries: OpenType tags, HarfBuzz’s tag table, a UCD subset and AGLFN.

Engineering and debugging

  • fea_check({snippet}) compiles a feature code fragment against the current glyph set with fontc and maps errors back to the line.
  • interpolation_check({glyphs?}) finds mismatched points, contours, components, anchors, start points and contour direction across drawings, written in TypeScript on Babelfont.
  • qa_checks({profile}) runs fontspector, the Rust port of fontbakery. It is alpha and covers about 81% of the universal profile.
  • ttx_dump({tables, glyphs?}) uses fontTools in Pyodide, for reading compiled GSUB and GPOS.
  • shape_compare({text, before, after}) diffs glyph runs between two builds.
  • kerning_query and find_glyphs answer structured questions without writing Python.
  • language_support({languages}) starts with a check against CLDR exemplar characters, with shaperglot WASM later.
  • recent_changes({since}) and project_notes: “what did I just break”, plus per-font conventions the assistant remembers.

# Models and prices

The assistant can work with several AI models. They differ in what they’re good at, how fast they answer and what a prompt costs. This page explains how the model picker gets its numbers and how Counterpunch decides where your prompt is sent. Everything here is measured and calculated automatically. You never have to set anything up.

## Picking a model

The chip under the prompt field shows the model for your next prompt and its price per prompt. Tap it to open the model picker. The glyph filter editor has the same chip, in both Simple and Expert mode, with its own saved choice, because filters are often simple enough for a cheaper model.

The picker has one column per model family. Open weight models are published openly by their makers (the small capitals under the name name the maker) and are run for us by several hosting companies. The other columns hold closed models, named after the company that makes them. DeepSeek Flash is the default. You can switch models at any point in a chat, and each reply is labelled with the model and version that wrote it.

## Zero data retention

Every model in the picker runs with zero data retention (ZDR): the company running the model may not store your prompts, your font data or the replies, and may not train on them. A model that can’t guarantee this isn’t offered at all. Counterpunch enforces it on every request, including retries.

## Quality

Each model shows a Quality line of one to five dots. It comes from two sources:

  • Our tests. Every night, each model runs a fixed set of font tasks on a test font, such as adding anchors at every station, writing a kern feature that compiles, writing a glyph filter, or reading text back from an image. The results are graded automatically. No user data is involved.
  • Real use. How often prompts finish without errors, with working code at the end, and without being stopped, retried or undone, and how people rate replies with the thumbs buttons. Only these outcomes are counted, never the content of your chats.

A new model starts with its test result, so it has dots from day one. Each finished prompt then moves the score a little. After a few hundred prompts, real use outweighs the tests.

## Badges

Three badges mark the current leaders: Cheapest, Fastest (shortest typical time from Send until the assistant has finished) and Best quality (the most Quality dots, with ties broken by the exact score behind them, so it reflects our tests, how prompts finish and your ratings together). Each belongs to the one model that leads that measure right now, and moves automatically when another model overtakes it. Every model can do the same tasks with the assistant’s tools, so the cards don’t describe what a model is “for”. Pick by what matters to you: quality or price, and the badges if speed matters.

## Price per prompt

The Per prompt line shows a range, such as 1–3 ct, and up to five coloured dots. A prompt is everything that happens after you press Send: the model’s reply and every tool it uses along the way.

  • The low end is what the first prompt of a chat costs on average.
  • The high end is what the costliest prompt of a chat costs on average. Prompts get more expensive as a chat grows, because the model rereads the whole conversation each time. Starting a new chat for a new task keeps prices near the low end.
  • Both are averages over the most recent 200 chats with that model, across all users, rounded to whole cents, at least 1 ct. The prices include all fees and VAT, so they match what is deducted from your credit.
  • Each dot stands for a price band: up to 3 ct, up to 10 ct, up to 25 ct, up to 50 ct, and above. The dots from the low end’s band to the high end’s band are lit, so you can compare models at a glance.

Only the cost and token counts of each prompt are stored for this, with a random chat number that isn’t linked to your account. Your prompts, replies and font are never stored.

## New models and versions

Each model has a version menu under its card. Latest is selected by default and moves to a new version only after that version has passed our requirements (image input, tool use, ZDR) and our tests. The menu also lists up to three specific versions, if you prefer to stay with one that works well for you. If a version you picked is withdrawn, your next prompt uses Latest instead and the chat says so.

A new version starts with the prices of the version before it, and real prices take over prompt by prompt. A model that is completely new has no history, so its price is estimated from the token prices its hosts advertise and from how many tokens it used in our tests. Estimated prices are marked with “≈” and drawn as rings instead of filled dots until enough real chats have finished.

## Where your prompt goes

Closed models always run with the same ZDR hosting partner, chosen by us. For open-weight models, Counterpunch picks the host for you: it only considers hosts that guarantee ZDR, handle images and tools correctly in our tests, and keep a good quality score. Among those, it prefers the one that is cheapest for a typical chat and fast.

Once a chat has started, it stays with the same host. The host keeps the conversation it has already read in a short-lived cache, which makes later prompts much cheaper and faster. A chat moves to another host only if the current one fails, or after the chat has been idle for more than 30 minutes, when the cache has expired anyway. If no host can answer for the model you picked, the chat shows an error with a Retry button. Counterpunch never switches you to a different model on its own.

## Overage

When your included credit for the month is used up and you have overage turned on, prompts cost twice the standard price. The picker then shows all prices doubled. See Subscription and usage.

## Models

## Chat history

Chats are saved on this computer, separately for each font. The clock button next to + lists the chats for the open font, newest first, with the model, the number of prompts and what the chat cost. Open one to see it exactly as it was and to carry on. + starts a new chat; the old one stays in the history. You can delete single chats or clear the history for a font. Chats in the glyph filter editor are kept until you close the tab and have no history. Clear chat empties the chat for the open filter.

## Feedback

Under the last reply of each prompt, thumbs up and down tell us how it went. Only the rating itself is counted, together with the model that answered, never your font or the chat. Ratings feed the Quality dots: a thumbs down counts the prompt as failed, and a thumbs up tells us that stopping, retrying or undoing on that prompt wasn’t a sign of a bad answer.

The assistant can take a snapshot of the text view, filled in as in preview mode, and look at it, for example to check spacing or spot a broken outline. Snapshots appear as thumbnails in the chat and are sent to the model like the rest of the prompt.

## What leaves your computer

A prompt sends your message, the chat so far, a compact summary of the editor state, the results of the tools the assistant used, and any snapshots it took. A complete font file is never sent. Every model runs with zero data retention: the company running it may not keep or train on any of this. Counterpunch stores only the cost, token counts and outcome of each prompt, without your account or any content. See Models and prices.

## What each tool may do

The tool list in the Assistant view marks every tool with one of three labels, and tool steps in the chat show the same label:

  • Read-only tools only look: at the font, the documentation, compiled binaries or a snapshot. They change nothing.
  • Consequential tools change something you can see and undo, such as the text in the editor, feature toggles, the open font or a Script Editor draft.
  • Unsafe tools run Python code, whose effect depends on the code. With Assistant editing off, the code still can’t change your font. With it on, the assistant says what the code will do before it runs, and Cmd/Ctrl+Z undoes the result.

## Credit

Every account includes assistant credit each month: €0.50 on the free plan, more on paid plans. Each prompt deducts its cost, which the model picker shows in advance as a range. Credit renews on the first of each month.

When your credit gets low, a small meter appears next to the model chip, such as “≈ 12 prompts left”. The number depends on the selected model, so a cheaper model gives you more prompts. Tap the meter to see the exact balance and the renewal date.

## Overage

On a paid plan you can turn on overage in your account. Once your included credit is used up, prompts then continue at twice the standard price and are added to your next invoice. The chat tells you when this starts, the meter reads “Overage · ×2”, and the model picker shows every price doubled. A prompt that uses up the last of your credit is billed partly from credit and partly at the overage price.

Without overage, the assistant pauses until your credit renews.

A higher plan includes more credit at standard prices before overage starts. If you often reach overage, compare plans in your account.
